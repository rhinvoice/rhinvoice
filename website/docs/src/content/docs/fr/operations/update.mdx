Pour mettre à jour Rhinvoice, indiquez la nouvelle version dans `.env`, récupérez les images et redémarrez les conteneurs. Les migrations de la base de données s’exécutent automatiquement au démarrage. Avant cela, lisez le changelog et faites une sauvegarde.

## Avant la mise à jour

- **Lisez le [changelog](https://github.com/rhinvoice/rhinvoice/blob/main/CHANGELOG.md).** Rhinvoice suit le Semantic Versioning; avant la 1.0, les versions mineures peuvent contenir des changements incompatibles. Les versions sont listées sous [GitHub releases](https://github.com/rhinvoice/rhinvoice/releases).
- **Faites une sauvegarde**, si vous en avez configuré une ([Sauvegarde et restauration](/docs/fr/operations/backup/)) :

  ```bash
  docker compose exec backup rhinvoice-backup backup    # sauvegarder maintenant
  ```

## Mise à jour

<Steps>

1. Seulement avec une version fixée : dans le dossier contenant `compose.yml` et `.env`, réglez `RHINVOICE_VERSION` dans `.env` sur la nouvelle version, par exemple `RHINVOICE_VERSION=0.8.3`. Avec `latest`, sautez cette étape.

2. Récupérez les images et redémarrez :

   ```bash
   # avec une version fixée : régler d’abord RHINVOICE_VERSION dans .env, puis
   docker compose pull
   docker compose up -d
   ```

3. Vérifiez que tout fonctionne : `docker compose ps` affiche « healthy » après quelques secondes.

</Steps>

Les migrations de la base de données s’exécutent automatiquement au démarrage (`RHINVOICE_RUN_MIGRATIONS=true` dans `.env`).

`compose.yml` fixe exactement les images de la base de données et de Gotenberg ; leurs correctifs de sécurité arrivent avec les versions de Rhinvoice. À chaque mise à jour, téléchargez donc aussi la `compose.yml` actuelle (`curl -fsSLO https://raw.githubusercontent.com/rhinvoice/rhinvoice/main/deploy/compose.yml`) ; vos réglages restent dans `.env`.

## Version fixée ou latest

`.env` détermine comment Rhinvoice suit les nouvelles publications :

| `RHINVOICE_VERSION` | Comportement |
|---|---|
| une version, par exemple `0.8.0` | fixée : ne change que si vous la changez |
| `latest` | suit chaque publication au prochain `docker compose pull` |

Une version fixée est le choix le plus sûr pour de vraies factures : vous décidez quand mettre à jour et pouvez d’abord lire le changelog.

<Aside type="note" title="Les factures émises restent telles quelles">
Une mise à jour ne modifie jamais les documents émis. Ils gardent leur contenu et leur PDF archivé. Une mise en page d’impression modifiée ne s’applique qu’aux nouveaux PDF.
</Aside>

## Avis de nouvelle version

Une fois par jour, Rhinvoice vérifie s’il existe une nouvelle version. Une carte apparaît alors en bas de la navigation avec le nouveau numéro de version, un lien vers les nouveautés et les étapes pour le serveur, prêtes à copier : la commande et, avant elle, la ligne pour `.env` si votre `.env` fixe une version. Avec `latest`, la carte n’affiche que la commande ; elle apprend comment `.env` est réglé par `compose.yml`, téléchargez donc la version actuelle lors de la prochaine mise à jour (avec une plus ancienne, la carte affiche la ligne avec « Seulement si .env fixe une version »). <Since version="0.8.4" /> *À propos de Rhinvoice* montre la même chose et indique si vous êtes à jour; **Rechercher des mises à jour** y lance la vérification tout de suite au lieu d’attendre le lendemain.

Pour la vérification, Rhinvoice télécharge un petit fichier signé de la dernière publication sur GitHub. Comme pour tout téléchargement, GitHub voit l’adresse de votre serveur; aucune donnée de votre installation n’est envoyée. Un fichier dont la signature ne correspond pas est écarté. Pour désactiver la vérification, indiquez dans `.env` :

```bash
RHINVOICE_UPDATE_CHECK=false
```

Dans le programme pour Windows et Mac, ajoutez la ligne `"update_check": false` au fichier `rhinvoice.json` du dossier de données (voir [où se trouvent vos données](/docs/fr/getting-started/install-desktop/#où-se-trouvent-vos-données)) et redémarrez Rhinvoice. <Since version="0.8.0" />

## Tester les versions candidates

Avant d’être publiée, une version paraît sur GitHub comme version candidate (une pré-publication étiquetée par exemple `v0.7.4-rc.1`). Normalement, Rhinvoice n’en propose jamais. Pour essayer les versions candidates sur une installation de test, indiquez dans `.env` :

```bash
RHINVOICE_UPDATE_CHANNEL=test
```

Pour Windows et Mac, une version candidate arrive comme programme distinct, **Rhinvoice Beta**, installé à côté de Rhinvoice avec ses propres données; il se voit proposer les versions candidates plus récentes comme mises à jour (voir [Rhinvoice Beta pour les versions candidates](/docs/fr/getting-started/install-desktop/#rhinvoice-beta-pour-les-versions-candidates)). Rhinvoice lui-même ne se voit jamais proposer de version candidate, quoi qu’indique `rhinvoice.json`. La vérification de la signature est la même que pour les publications.

<Aside type="caution">
Les versions candidates servent aux tests. Utilisez-les avec des copies de vos données, pas pour les factures que vous envoyez.
</Aside>

## Quelle version est-ce que j’utilise?

La version est affichée en bas de la navigation, à côté de « by webberz ». Un clic ouvre *À propos de Rhinvoice*, avec un lien vers *Nouveautés*.
